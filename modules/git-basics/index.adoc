== Four places, not one

Most confusion with git comes from believing a file is simply "saved or not".
A change passes through four places, and every git command you will type moves
it between two of them.

[source,bash]
----
git init                    # start a repository in this directory
git status                  # which files are where
git add report.adoc         # working tree -> index
git commit -m "Add report"  # index -> local repository
git log --oneline           # read the history
git restore report.adoc     # index -> working tree, throw the edits away
----

`git status` answers the only question that matters while you work: what is in
which state right now. Run it more often than you think you need to.

== The remote is a repository, not a headquarters

`origin` on the server holds the same kind of history as `.git` on your machine
— a full copy, not a master version that yours is a fragment of. This is what
*distributed* means: any clone can be used to continue the work if the server
burns down.

Two consequences you feel on the first day:

* `git add`, `git commit`, `git log` and `git diff` never touch the network.
  Committing on a train works. Only `git push`, `git fetch`, `git pull` and
  `git clone` cross the line in the picture.
* A commit that exists only in your local repository exists for nobody else.
  "It is committed" and "the others have it" are two different statements — the
  second one needs a push.

NOTE: How the two sides are kept in step — remote-tracking branches, conflicts,
rejected pushes — is the subject of `git-conflicts-remotes`. Here it is enough
to see where the line runs.

== What a commit is

A commit records the *complete state* of the tracked files, plus who made it,
when, and a message. It is not a diff — the diff is computed between two
commits when you ask for it.

[source,bash]
----
git log --oneline --graph
git show <hash>             # what this commit changed
git diff                    # working tree vs index
git diff --staged           # index vs last commit
----

Because a commit is a state, you can always go back to one. That is the actual
promise of version control: you can experiment because you can return.

== Commit messages

The message is written for a person reading the history later — usually you, and
usually while looking for the moment something broke.

[cols="1,1",options="header"]
|===
|Useless |Useful

|`update`
|`Fix off-by-one in attendance count`

|`stuff`
|`Add initial situation to config.yaml`

|`fix bug`
|`Reject bookings for slots that already started`
|===

Rule of thumb: the subject line says *what changes for the reader*, in the
imperative, under about fifty characters. If you need to explain *why*, add a
blank line and a paragraph — that is where the reasoning belongs, not in the
code as a comment nobody updates.

== What does not belong in a repository

[source,gitignore]
----
build/
target/
node_modules/
.venv/
.env            # secrets
*.class
.DS_Store
----

Two categories: things you can regenerate, and things that must not be public.
A secret committed once stays in the history even after you delete the file —
removing it means rewriting history, which is a bad afternoon. Check *before*
you commit.

== Decisions

* Every project in this course lives in a git repository from the first day, not
  from the first milestone.
* Documentation is committed together with the code it describes. Same
  repository, same history.
* Generated output is never committed. If it can be rebuilt, it is not a source.
* Commit messages are in English, imperative mood, subject under fifty
  characters.

== Pitfalls

* One giant commit at the end of the evening. The history then says nothing, and
  bisecting a bug is impossible.
* `git add .` without looking. That is how `node_modules` and `.env` get in.
* Committing generated HTML next to the AsciiDoc source. Two truths, and the
  diff becomes unreadable.
* Believing a file is "in git" because you saved it. Saving writes the working
  tree; only `git commit` records it.
* Believing a commit is safe because it is committed. It lives on one disk until
  it is pushed — the machine in room 3 is not a backup of itself.
